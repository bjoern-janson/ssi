## Classification rule

Use the shallowest sufficient class:

```text
H1 = implementation / orchestration defect
```

A case is H1 only if the semantic distinction needed for the expected result is already represented and an existing R1..R11 jurisdiction already owns the operation. A case is H3 only if the required derivation/refusal cannot be expressed through any existing rule jurisdiction even with adequate representation and correct execution semantics.

## The important change from H24

H24 exposed many local orchestration defects and led to a successor that successfully generalized route composition to deeper and longer paths.

HF16 moves the failure locus one level lower.

Four of five failures are generated by the same implementation defect:

```text
AUTHORITY_LIVENESS_VIEW
```

The schema already distinguishes:

```text
CONSTITUTED
SCOPED
UNRESOLVED
WITHDRAWN
PROVENANCE_ONLY
```

but the frozen rule matchers do not uniformly consume a view of **currently live authority**. Selected successor orchestration gates use `ActiveAuthority`; other rule-local predicates still inspect raw fact presence.

That creates both directions of error:

```text
WITHDRAWN / UNRESOLVED positive fact
    -> prematurely authorizes

WITHDRAWN negative fact
    -> prematurely refuses
```

So the stronger implementation law is not another per-rule guard. It is:

> **Every rule premise that claims current authority must be evaluated against a live-authority view by default; historical/provenance access must be explicitly requested for lineage-only reasoning.**

This preserves the distinction discovered in CASE-101:

```text
usable as lineage
!=
usable as authority
```

## Architectural diagnosis

The H24 successor was a successful **route-composition repair**, but not yet a true derivation-state substrate.

The fresh result says the next evaluator architecture should move these mechanisms *beneath* rule-specific matching:

```text
raw facts
    -> historical lineage view
    -> live authority view
    -> typed current obligations
    -> rule applications
    -> bridge discharge / subgoal generation
    -> certificate
```

rather than:

```text
raw facts
    -> rule-specific matcher
    -> selected orchestration patches
```

That is a materially different implementation target, while still leaving the R1..R11 rule partition unchanged.
